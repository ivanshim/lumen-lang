# Language definitions

One JSON file per language. Each file maps a fixed set of labels, the names
of things the kernel can do, to the strings a language spells them with. The
files are reference definitions of the surface syntax; the semantics behind
every label belong to the kernel and are the same for every language.

Status: these files are not yet read by either kernel. The microcode kernel
still loads the YAML schemas in `kernels/microcode/schemas/`, and the
Python-like and Rust-like examples still use Lumen spellings. Wiring a JSON
loader to these files, with a validator, is the next step. `lumen.json`
describes what runs today; the other three describe the target language and
carry labels the kernels cannot honour yet (listed below).

## Format rules

1. A file is one flat JSON object. Every file carries the same labels in the
   same order; `scripts/config_table.py` fails if they differ.
2. Lexeme labels take a list of strings. The first entry is canonical and is
   what the kernel uses when it renders a value or names a token in an error.
   Later entries are aliases. An empty list means the language has no
   spelling for that label.
3. Setting labels take a JSON scalar of the setting's type: `true`/`false`,
   a number, or a string. `null` means the setting does not apply.
4. `op.precedence` is a list of tiers, lowest first, each tier a list of
   lexemes. Precedence is keyed by lexeme, not by label, so two aliases of one
   operation may sit in different tiers (PHP's `and` and `&&`). Unary
   operators are listed in their own tier. `op.right_associative` names the
   lexemes that associate to the right.
5. Keys beginning with `$comment` are ignored by loaders.
6. A lexeme may appear under at most one label per parsing position. `-`
   under both `op.sub` (infix) and `op.negate` (prefix) is allowed; the same
   string under two infix labels is an error.
7. Every lexeme under `stmt.*` and `literal.*` is a reserved word.
8. `format_version` identifies the label set. A loader rejects unknown keys
   and wrong value types.
9. Identifier characters are a kernel policy selected by `identifier.unicode`:
   underscore always, then letters and digits from ASCII or from all of
   Unicode. Keywords and operators are always ASCII.

## Labels without a kernel path yet

These appear in the target definitions and describe real syntax, but neither
kernel implements them. Each is a kernel change, not a config change:

- `lexical.comment_block.*`, `lexical.prologue`, `lexical.number.hex_prefix`,
  `identifier.variable_prefix`, `lexical.keywords_case_insensitive`: the
  ingest stages hardcode comment, number and word shapes.
- `syntax.map.*`: no map value in the kernel.
- `stmt.foreach.*`, and `stmt.for` over a collection rather than a range: no
  iteration over collections.
- `stmt.emit`: output as a statement rather than a call.
- `builtin.range`: the range operation exists but has no builtin name.
- Rust's `println!`, `print!` and `panic!`: the macro suffix is not a word
  character.
